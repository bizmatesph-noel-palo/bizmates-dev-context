## The Question

What prefix should the 10 new ASC allocation tables use?

| Option | Prefix | Example | Convention source |
|---|---|---|---|
| **A** | `asc_alloc_*` | `asc_alloc_calculation_runs` | Kuroda-san's DB design (REF-CAP-04) |
| **B (proposed)** | `log_*` | `log_alloc_calculation_runs` | Existing accounting system convention |

---

## Current System Convention

From the Bizmates database (confirmed via ls-database-migrations + model `$table` properties):

| Prefix | Role | Examples in the accounting system |
|---|---|---|
| `mst_*` | Master / reference data (rarely changes) | `mst_rule_for_journals`, `mst_code_change`, `mst_product` |
| `trn_*` | Transactional data (created by upstream systems) | `trn_charge`, `trn_student_product`, `trn_ticket` |
| `log_*` | **Computed / batch-generated data** (created by our batch commands) | `log_daily_rate_calculation`, `log_sum_calculation`, `log_monthly_rate_calculation`, `log_send_journals_history`, `log_balance_transition` |

**Key observation:** Every table that the accounting batch WRITES TO uses the `log_*` prefix. The `log_*` prefix in this system doesn't mean "append-only logs" — it means "data generated by batch processing." This includes:
- Calculation results (`log_daily_rate_calculation`)
- Aggregations (`log_sum_calculation`)
- Send history (`log_send_journals_history`)
- Balance tracking (`log_balance_transition`)

The ASC allocation tables are the same category — data generated by batch processing.

## Proposal: Use `log_alloc_*` Prefix

| # | Kuroda-san design (asc_alloc_*) | Proposed (log_alloc_*) | Role |
|---|---|---|---|
| 1 | `asc_alloc_calculation_runs` | `log_alloc_calculation_runs` | Run lifecycle tracking. Records each batch execution (preview/final), status, timing, error messages. Needed for: audit trail, failure detection, idempotency. |
| 2 | `asc_alloc_source_documents` | `log_alloc_source_documents` | Immutable snapshot of input data (original N values) before overwrite. Needed for: audit — proves what the values were before allocation modified them. |
| 3 | `asc_alloc_bundles` | `log_alloc_bundles` | Bundle header — one row per detected Coaching+App pair per run. Needed for: tracking which charges were identified as bundles, match_rule traceability. |
| 4 | `asc_alloc_bundle_charges` | `log_alloc_bundle_charges` | Products within a bundle (coaching + app rows). Needed for: linking individual charges to their bundle, supporting multi-product detection. |
| 5 | `asc_alloc_groups` | `log_alloc_groups` | One bundle × one month. Holds ΣN, ΣP, is_balanced flag. Needed for: validation (V-1: ΣP = ΣN), monthly grouping. |
| 6 | `asc_alloc_prorations` | `log_alloc_prorations` | **Core result table.** One row per product per group. Stores L, ratio, N, P. Needed for: the actual allocation result, CSV generation, Metabase breakdown. |
| 7 | `asc_alloc_reference_prices` | `mst_alloc_reference_prices` | Allocation weights (effective-dated). **Note: this is master data, not batch output — uses `mst_*` prefix.** Needed for: configurable L values without code changes. |
| 8 | `asc_alloc_sum_calculation` | `log_alloc_sum_calculation` | Freee-level aggregation. Needed for: tracking what was sent to Freee (if we ever need to reconcile). |
| 9 | `asc_alloc_sum_calculation_history` | `log_alloc_sum_calculation_history` | Trace: which proration rows → which summary row. Needed for: audit trail from Freee journal back to individual allocations. |
| 10 | `asc_alloc_deliveries` | `log_alloc_deliveries` | Delivery attempt tracking (Freee/CSV/email). Needed for: retry logic, failure tracking. |
| 11 | `v_asc_alloc_prorations_active` | `v_alloc_prorations_active` | View for active-run queries. |

## Why `log_alloc_*` (Not `asc_alloc_*`)

### 1. Consistency with existing codebase

Every batch-generated table in the accounting system uses `log_*`. Introducing a different prefix (`asc_alloc_*`) creates a naming inconsistency that:
- Confuses developers about which convention to follow for future tables
- Makes `SHOW TABLES LIKE 'log_%'` miss allocation tables
- Breaks the mental model: "all batch output lives under `log_*`"

### 2. The `asc_` prefix implies project ownership, not data category

`asc_alloc_*` says "this belongs to the ASC allocation project." But table naming should reflect **what the data IS** (its role in the system), not **which project created it**. Projects are temporary; tables are permanent. Once deployed, these tables are just part of the accounting system — they don't "belong to" a project anymore.

Analogy: `log_daily_rate_calculation` is not named `ascm_daily_rate_calculation` even though the ASCM project created it. It's named by what it IS.

### 3. Reference prices are master data — should use `mst_*`

`asc_alloc_reference_prices` stores L values (¥3,980, ¥19,800, etc.) that are configured once and rarely change. This is classic master data — same category as `mst_rule_for_journals` or `mst_code_change`. Using `log_*` for this table would be wrong. Under the `log_alloc_*` proposal, this becomes `mst_alloc_reference_prices` — matching its actual role.

Under `asc_alloc_*`, ALL tables get the same prefix regardless of their role, which loses this semantic information.

### 4. How similar systems approach this

**Stripe (Revenue Recognition):** Tables are named by function (`revenue_schedules`, `recognition_transactions`, `allocation_details`) — not by project or team. The naming reflects the data's role in the ledger.

**NetSuite (Revenue Allocation):** Uses functional prefixes (`RA_CALC_`, `RA_RULE_`, `RA_HIST_`) where RA = Revenue Allocation as a domain concept, not a project name.

**Our proposed `log_alloc_*`** follows this pattern — `alloc` is the domain concept (allocation), `log_` is the data category (batch-generated). It's both consistent with existing conventions AND descriptive of what the data is.

## If Kuroda-san Prefers `asc_alloc_*`

Both work. The system won't break either way. The arguments above are about **long-term maintainability and convention consistency** — not technical correctness. If there's a strong reason to keep `asc_alloc_*` (e.g., Accounting team already has Metabase queries drafted with that prefix, or the prefix helps them identify allocation tables visually), that's a valid reason to keep it.

**The one thing I'd still recommend regardless:** Split the reference prices table to `mst_*` prefix (or `mst_alloc_*`). This table is semantically different from the others — it's configuration, not batch output.
