# [ASC-261]
Carried-Over Lessons Not Calculated Correctly for Multi-Month Charges After ASC-260 Fix

## [Story]
Following the deployment of the ASC-260 fix, a regression has occurred where carried-over lessons are no longer correctly passed to the following month.
This issue affects charges whose ticket validity spans across multiple months (60-day validity window) past their contract end date. The system is dropping the carried-over counter to 0 in the subsequent month, causing incorrect expired and paid_price calculations.

## [Precondition]

* **Student ID:** 181524
* **Order No:** 10021998
* **Charge ID:** 2880532
* **Plan Type:** 8 lessons / month (Unit price calculation basis: ¥1,320 per lesson)
* **Contract Period:** 2/11 ~ 3/10
* **Ticket Expiration Date:** 4/10 (60 days from the 2/11 start date)
* **Initial Usage (2/11 ~ 3/31):** 5 lessons taken (Leaving 3 lessons remaining to carry over into April)

## [Steps]
1. Set up historical records for Charge 2880532 showing 5 lessons taken prior to April.
2. Run the monthly calculation batch for April data (target_ym=202604) on Dev04 (Execution date: 2026-05-01).
3. Extract the row for `charge_id 2880532` from the output.

## [Expected]
**① April Data : 202604 CSV**
File: 202604_03_MonthlyRateCalculation([YYYYMMDD]).csv
target_ym,student_id,order_no,charge_id,total,number_of_carried_over_lessons,number_of_lessons_taken,number_of_expired_lessons,number_of_remaining_lessons,paid_price
202604,181524,10021998,2880532,8,3,1,2,0,3960

File_Note:
The 3 remaining tickets must carry over into April (`carried_over=3`).
With 1 lesson taken and the final 2 tickets hitting their 60-day expiry on 4/10 (`expired=2`), the correct paid price is 3,960 (¥1,320 × 3).

## [Actual]
**① April Data : 202604 CSV**
File: 202604_03_MonthlyRateCalculation([YYYYMMDD]).csv
target_ym,student_id,order_no,charge_id,total,number_of_carried_over_lessons,number_of_lessons_taken,number_of_expired_lessons,number_of_remaining_lessons,paid_price
202604,181524,10021998,2880532,8,0,1,0,0,1320

Actual_Note:
The system sets `carried_over=0` and fails to register that 2 tickets expired on 4/10.
It only bills for the 1 lesson taken, causing a revenue mismatch (1320 instead of 3960).

## [Comparison]
* **number_of_carried_over_lessons:** Expected 3, Actual 0
* **number_of_expired_lessons:** Expected 2, Actual 0
* **paid_price:** Expected 3960, Actual 1320

## [Acceptance Criteria]
* Ensure the fix implemented in ASC-260 does not clear or suppress `number_of_carried_over_lessons` for valid 60-day active windows.
* When an ongoing charge carries over into a second month, the starting `carried_over` balance must equal the previous month's final `remaining` balance.
* Remaining unspent tickets must be accurately processed through the expiration logic on their exact 60-day deadline date (4/10) and properly reflected in the `paid_price` sum.
