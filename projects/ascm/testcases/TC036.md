# [ASC-311]
Post-Processing Correction for Premature Expiry — Cross-Month FLP Charges

[Story]
When a monthly-plan charge has `end_date` on day 1 or 2 of the following month and the student has no successor charge (e.g., REST requested), the Grouped CTE's lookahead condition fires `is_ticket_expiry_month = 1` one month too early. This causes all remaining tickets to be marked as expired in the prior month with full `paid_price`, when they should remain as `remaining` with `paid_price = 0` until the actual expiry month.

ASC-311 implements a post-processing correction: after the CTE results are inserted into `log_monthly_rate_calculation` / `log_monthly_rate_calculation_pre`, a detection query finds these premature expiry rows and an UPDATE corrects them in-place before the transaction commits.

[Precondition]
* **Student ID:** S00000121073
* **Plan:** 月15回プラン (15 lesson plan, product_id 29, FLP)
* **Charge:** 3001753 (paid_price = ¥14,850, start_date = 2026-04-03, end_date = 2026-05-02)
* **Lessons taken:** 0
* **Successor charge:** None (student requested REST)
* **Target batch:** target_ym = 202604 (April 2026)
* **Why this charge triggers the bug:**
  - `end_date (2026-05-02) > LAST_DAY('2026-04-01') = 2026-04-30` → TRUE
  - `end_date (2026-05-02) <= DATE_ADD('2026-04-30', INTERVAL 2 DAY) = 2026-05-02` → TRUE
  - No successor exists → NOT EXISTS = TRUE
  - Lookahead fires → `is_ticket_expiry_month = 1` in April (premature)

[Steps]
1. Run `MonthlyRateCalculationCommand` for target_ym = 202604.
2. CTE generates rows and INSERTs into `log_monthly_rate_calculation`.
3. Post-processing detection query runs (within same transaction):
   ```sql
   SELECT m.id, m.charge_id, m.total, m.number_of_lessons_taken,
          m.number_of_expired_lessons, m.number_of_remaining_lessons, m.paid_price
   FROM log_monthly_rate_calculation m
   JOIN trn_charge c ON m.charge_id = c.id
   WHERE m.target_ym = '202604'
     AND c.end_date >= '2026-05-01'
     AND m.number_of_expired_lessons > 0
     AND m.number_of_remaining_lessons = 0;
   ```
4. Detection identifies charge 3001753 as premature expiry.
5. Correction UPDATE applies:
   - `number_of_expired_lessons` → 0
   - `number_of_remaining_lessons` → 15 (was expired)
   - `paid_price` → ROUND(14850 / 15 × 0) = 0 (recalculated for taken only)
6. Transaction commits with corrected data.

[Detection Query Logic]

Wu-san's confirmed detection query (parameterized):

```sql
SELECT m.*
FROM log_monthly_rate_calculation m
JOIN trn_charge c ON m.charge_id = c.id
WHERE m.target_ym = {targetYm}
  AND c.end_date >= '{firstDayOfNextMonth}'
  AND m.number_of_expired_lessons > 0
  AND m.number_of_remaining_lessons = 0;
```

Where:
- `{targetYm}` = the target_ym just inserted (e.g., `202604`)
- `{firstDayOfNextMonth}` = first day of the month after target (e.g., `2026-05-01`)

Key design decisions (Wu-san):
- **No product_id filter** — affects all monthly plans on both Bizmates and Zipan
- **Scoped to current target_ym only** — only fixes just-created records, won't touch historical data already in `log_sum_calculation`

[Correction Logic]

For each detected row:

```sql
UPDATE log_monthly_rate_calculation
SET number_of_expired_lessons = 0,
    number_of_remaining_lessons = number_of_expired_lessons,
    paid_price = ROUND((
        (SELECT paid_price FROM trn_charge WHERE id = log_monthly_rate_calculation.charge_id)
        / total
    ) * number_of_lessons_taken)
WHERE id IN (detected_ids);
```

Correction formula:
- `expired` → 0
- `remaining` → what was `expired` (these lessons haven't actually expired yet)
- `paid_price` → `ROUND(charge_paid_price / total × taken)` (revenue only for lessons consumed)

When `taken = 0`: `paid_price = ROUND(14850 / 15 × 0) = 0` ✓

[Acceptance Criteria]
* Post-processing runs within the same transaction as the INSERT (atomic — either both succeed or both roll back).
* Only rows matching the detection criteria for the current `target_ym` are updated.
* No historical records (prior target_ym values) are modified.
* The correction is applied to BOTH Bizmates (`log_monthly_rate_calculation`) and Zipan (`log_monthly_rate_calculation`) connections.
* The correction is applied in BOTH Final (`MonthlyRateCalculationLogic`) and Pre (`MonthlyRateCalculationPreLogic`) commands.
* Downstream processing (CalculationSummary, Freee journals) consumes the corrected data automatically (no changes needed there).
* Logging: the number of corrected rows must be logged (e.g., `[POST-FIX ASC-311] Corrected N row(s)`).

[Regression Check — Existing TCs Must Not Be Affected]

The post-processing only triggers when ALL conditions are met:
1. `target_ym` matches current batch (scoped)
2. `c.end_date >= first day of next month` (charge crosses month boundary)
3. `number_of_expired_lessons > 0` (expiry has been set)
4. `number_of_remaining_lessons = 0` (all tickets exhausted)

Charges that legitimately expire within their own month (end_date ≤ LAST_DAY) will never match condition #2. Charges with successors won't match because the CTE doesn't fire expiry for them (NOT EXISTS blocks it). Therefore no existing TC output changes.
