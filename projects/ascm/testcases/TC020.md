# [ASC-236]
Bizmates REFUND — Partial Refund Doubled and Incorrectly Persists

[Story]
There are two critical issues with partial refund processing in the monthly reports. First, the refund amount is being doubled (calculated as -14,850 instead of the actual -7,425). Second, this incorrect refund record is "leaking" into subsequent months; it appears in the March report (February data) despite only occurring once in January.

[Precondition]

* **Student:** 287046
* **Original Charge (2931293):** 月15回プラン | Price: 14,850 JPY | Period: 2026-01-19 to 2026-02-18
* **Partial Refund (2933642):** -7,425 JPY | Issued in January (paid_at: 2026-01-21)

[Steps]

1. Issue a partial refund of -7,425 in January.
2. Generate the February report (target_ym=202601).
3. Generate the March report (target_ym=202602).
4. Search for student_id "287046".

[Expected]
**① February Report (Jan Data): 202601 CSV**
File: 202601_03_MonthlyRateCalculation(20260201).csv

```csv
target_ym,student_id,department_id,order_no,charge_id,total,number_of_carried_over_lessons,number_of_lessons_taken,number_of_expired_lessons,number_of_remaining_lessons,paid_price
202601,287046,0,,2931293,15,0,4,0,11,3960
202601,287046,0,,2933642,,,,,,-7425
```

*Note: The refund row must use charge_id 2933642 (the refund transaction's own ID, per ASC-244 fix) with paid_price=-7425 (exact amount, not doubled).*

target_ym,student_id,department_id,order_no,charge_id,total,number_of_carried_over_lessons,number_of_lessons_taken,number_of_expired_lessons,number_of_remaining_lessons,paid_price

[Acceptance Criteria]

* Partial refund amounts must match the actual transaction value exactly (no doubling).
* Refund rows must use the refund transaction's own charge_id (2933642), not the original charge_id.
* Refund records must only appear in the report corresponding to the `target_ym` in which the refund was executed.
* Ensure the logic for "Carry Over" does not mistakenly include refund-type transactions in subsequent monthly aggregates.
