[Story]

Code analysis shows that an overly aggressive exclusion block in the `FilteredUsage` logic expels rows based strictly on the contract `end_date` without checking whether the tickets are still actively valid in the reporting month. This bug triggers whenever a separate, newer order number exists for the student.

### [Technical Analysis and Root Cause Hook for Devin AI]

The expulsion block in the `FilteredUsage` CTE filters out the February row because all three sub-conditions evaluates to true:

```sql
AND NOT (
    mu.lessons_taken = 0                                       -- TRUE (0 lessons taken)
    AND DATE_FORMAT(mu.end_date, '%Y-%m-01') < mu.month_start  -- TRUE (End of Jan < Feb batch start)
    AND EXISTS (異なるorder_noの後続あり)                       -- TRUE (Order 10029227 exists)
)

```

The query currently assumes that if the contract period ended in a previous month (`end_date < month_start`) and a new order exists, the data is dead. It completely fails to cross-reference ticket expiration parameters. A charge with 60-day ticket validity must not be dropped while its tickets are active within the batch window.

[Acceptance Criteria]

* Modify the `AND NOT (...)` expulsion conditions inside the `FilteredUsage` tracking routine to verify ticket lifespan windows instead of evaluating the contract `end_date` boundary exclusively.
* Ensure that if tickets from an older order are alive and hitting their 60-day expiry threshold inside month N+1, the row is preserved, metrics are printed, and revenue is captured.
* Prevent data leakage where rows are deleted and unspent ticket allocations are zeroed out without a formal balancing ledger transaction.
