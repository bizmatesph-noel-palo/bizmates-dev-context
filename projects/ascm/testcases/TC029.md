# [ASC-267]
Last Charge in Order Incorrectly Appears in Following Month's CSV (TicketMonths Leak Bug)

[Story]
A charge that serves as the final charge in its contract order string and ends in month N is incorrectly appearing in the month N+1 CSV output report. While the month N calculation data is completely accurate, the system's `TicketMonths` recursive expansion script over-extends the data lifecycle into the next month. This happens because the existing expulsion rules fail to capture rows that do not have a subsequent contract order line item attached to the account.

[Precondition]

* **Student ID:** 278204
* **Order No:** 10022146
* **Charge ID:** 2741663
* **Position:** Last charge of this order string.
* **Charge Period:** 2026-02-01 – 2026-02-28
* **Status:** The month 202602 calculations are fully correct and complete. No subsequent order (`order_no`) lines exist for this student account.

[Steps]

1. Populate data tables with final Charge 2741663 under the February 2026 cycle.
2. Ensure there are no subsequent orders mapped for this student profile.
3. Run the processing data validation pipeline for the March report cycle (target_ym=202603).
4. Inspect the output dataset specifically looking for `charge_id 2741663`.

[Expected]
**March report (Feb Data) : 202603 CSV**
*Row for charge 2741663 should not appear at all.*

[Actual]
**March report (Feb Data) : 202603 CSV**
target_ym,charge_id,total,number_of_carried_over_lessons,number_of_lessons_taken,number_of_expired_lessons,number_of_remaining_lessons,paid_price
202603,2741663,8,1,0,1,0,1254

*Actual_Note: The charge leaks out into March processing records, displaying ghost carry-over balances and a phantom paid_price calculation of 1,254.*

### [Technical Analysis and Root Cause Hook for Devin AI]

The logic leak stems from two system intersections during calculations:

1. **TicketMonths Expansion Error:** The ticket's `end_datetime` boundary includes a standard 60-day validity calculation window. This causes the recursive `TicketMonths` expansion loop to mistakenly build a tracking segment for March:
```text
DATE_ADD('2026-02-01', INTERVAL 1 MONTH) = '2026-03-01' < DATE('2026-04-01') → TRUE

```


2. **Exclusion Guard Flaw:** Inside the `FilteredUsage` logic script, the `OR` block allows this phantom March record to pass through because there is no different-order successor item. This causes the code segment evaluation `NOT EXISTS (different order_no successor)` to return `TRUE`.

Because the system's current `AND NOT` expulsion guard condition only fires when a newer order *does* exist (`EXISTS(...) = TRUE`), this final dead-end charge row bypasses protection completely and bleeds into production tables.

[Acceptance Criteria]

* Adjust the `FilteredUsage` or `TicketMonths` boundary evaluations to ensure that a contract order's last charge row cannot generate records in month N+1 if its formal contract lifecycle terminated inside month N.
* Expand the expulsion block rules to verify order boundary conditions independently of whether a follow-up contract order has been logged.
* Eliminate phantom rows from appearing inside subsequent processing cycles when contract timelines are completely closed.
